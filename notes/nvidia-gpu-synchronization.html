NVIDIA GPU · software × hardware pipeline

一块 Tile
的八次交接

从 CPU submission、grid admission 和 warp issue，到 TMA、mbarrier、Tensor pipeline、remote completion 与 storage reuse。同步不是一串 API，而是下一阶段获得“可以继续”的凭证。

scoreboard ≠ barrier completion ≠ visibility full ≠ reusable progress is a proof
一个独立推进的 agent 把数据、完成状态或资源所有权交给另一个 agent；同步协议要证明后者现在能安全、可见、并且最终可前进地继续。

00 · Workload

先定义这块 tile 从哪来、要去哪

全文追踪一个 tiled GEMM 的输出工作单元 Tile T₀。它由 block 坐标定义，并接收沿 K 维展开的 R 对 A/B input tiles；绿色输出不是某一对输入的结果，而是整条 reduction 完成后的计算 lineage 终点。

workload contractC_T₀ ← init(C_T₀) + Σᵣ Aᵣ × Bᵣ
AM × K
M ↓K → A₀BM × BK A₁BM × BK … AᵣBM × BK
×相同 r 配对
BK × N
K ↓N → B₀BK × BN B₁BK × BN ⋮ BᵣBK × BN
ΣᵣR 次 fan-in
CM × N
M ↓N → Tile T₀all R slices · BM × BN
tile_kernel(block_m, block_n)

一个 CTA 负责输出窗口 C[m₀:m₀+BM, n₀:n₀+BN]。令 R = ceil(K/BK)：它必须取得 R 对 Aᵣ / Bᵣ，并把每一对的 partial product 累加到同一个 T₀ accumulator。

K-reduction fan-inR = ceil(K / BK)
r = 0ΔC₀ = A₀ × B₀ r = 1ΔC₁ = A₁ × B₁ … r = R−1ΔCᵣ = Aᵣ × Bᵣ
同一块 BM × BN register tileAcc_T₀ += ΔCᵣ循环 R 次后才能 store

关键：一对 Aᵣ / Bᵣ 只贡献一份 ΔCᵣ；它不是 C_T₀。只有所有 r 的 contribution 都累加完成，Acc_T₀ 才能 materialize 为 global-memory C_T₀。

T₀ 是一张计算工单，不是一块一路搬运的内存

T₀ = (block_m, block_n) 只表示“计算 C 的这一块输出”。开始时只有它依赖的 A/B tiles；计算中 shared memory 保存临时 K-slices，registers 保存部分和；K-loop 完成后，它才成为 C 中真实存在的 output tile。

为什么同步要强调这一点？

  • CUDA event确认产生 A/B inputs 的 upstream work 已完成，tile_kernel 可以消费。
  • Scoreboard确认 load 的目标 register ready，dependent instruction 可以 issue。
  • Barrier / mbarrier确认 shared 中当前 K-slice 已发布，或 async transaction 已完成。
  • Empty permit确认 consumer 已用完 S0/S1，producer 才能覆盖复用。
  • Kernel event确认最终 C_T₀ 已写完，downstream task 才能接手。

共同点不是同一段 bytes。这些 receipt 分别关闭不同对象上的依赖边；它们只是共同服务于“完成 T₀ 这张工单”。

02 · Contract

每次交接，都写四份证明

P/C/V/O 不是按顺序推进的四个阶段，而是检查同一张 receipt 覆盖了哪些义务。Participants、scope、phase/generation 是证明参数；wait 时仍持有的 registers、shared memory、CTA slot 和 queue resource 决定协议是否高效、甚至是否能前进。

P

Progress

Producer 与 required participants 最终能获得调度机会吗？等待者会不会占满 producer 需要的 residency resource？

C

Completion

Consumer 等到的究竟是 launch-ready、register-ready、transaction complete，还是 whole-grid complete？

V

Visibility

观察 completion 后，payload 是否按正确 memory order、thread scope 和 proxy contract 可见？

O

Ownership

Consumer 用完以前，storage 会不会被下一代 tile 覆盖、释放，或被另一个 API 重新取得？

Producer instruction
→ dependent instruction

PUBLICATION

Producer threads
→ shared-memory consumers

Register ready 只让 producer instruction 继续。多个 producers 把 Aᵣ / Bᵣ fragments 组装进 shared stage 后，一个 warp 的 scoreboard 仍无法把它发布给其他 consumers；这里必须换成跨-thread receipt。

05 · Diagnose

Tile 停在哪张 receipt 前？

选择一个 profiler 或 correctness 症状。诊断不先猜 API，而是定位 work、data 或 ownership chain 的断点。

Completion gate · scoreboard

Producer result latency 正在暴露

Dependent instruction 在等 global/local/texture path 返回 register result。它首先是 instruction dependency，不是 participant synchronization。

  • 检查 coalescing、cache locality 与 memory path。
  • 用 independent arithmetic 增加 ILP。
  • 确认是否有足够的其他 eligible warps 覆盖 latency。

06 · Generations

主线稳定，凭证实现会变化

不要把一代 GPU 的指令路径推广成 NVIDIA GPU 的永恒实现。稳定的是四份证明；变化的是 agent、completion object、scope、proxy 与 lifetime rule。

Pascal & earlier

旧 lockstep 心智

Legacy warp-synchronous 代码需要重新检查 participant 与 memory ordering。

Volta / Turing

Independent scheduling

Sub-warp divergence 使 mask 与 logical participant set 必须显式。

Ampere

Async copy

cp.async、group wait 与 pipeline state 从普通 register chain 中拆出。

Hopper

TMA + mbarrier

Cluster、DSM、tx-count、WGMMA、PDL 与 memory domains 扩展交接面。

Blackwell generation

Tensor Memory

tcgen05、CLC 与 specialized completion 增加新的 resource lifetime。

Final model

看到任何同步原语，先把 tile 放回流水

最窄 scope、最小 participants、最精确 completion、最晚必要 wait。不要追求“最强同步”，要追求责任刚好匹配的交接。

  • 谁生产，谁消费？
  • Producer 一定能被调度吗？
  • 等到的是哪一种 completion？
  • Scope、order、proxy 是否匹配？
  • Wait 时仍占着什么硬件资源？
  • 谁把 ownership 交回下一代？
